# **Структуры данных в Python: устройство и асимптотика**

## **List (список) - динамический массив**

### **Внутреннее устройство**

Список в Python - это **динамический массив указателей** на объекты. Он хранит не сами объекты, а ссылки на них в непрерывном блоке памяти.

```
Список [1, 2, 3] в памяти:
┌─────────────────┐
│  List Object    │
│  ├─ size: 3     │
│  ├─ allocated: 4│  ← выделено места на 4 элемента
│  └─ items ──────┼──► [ptr1] [ptr2] [ptr3] [NULL]
└─────────────────┘      ↓      ↓      ↓
                        int(1) int(2) int(3)
```

**Ключевые особенности:**
- Непрерывный блок памяти для указателей
- При переполнении выделяется новый блок с запасом (over-allocation)
- Формула роста: `new_allocated = newsize + (newsize >> 3) + (3 if newsize < 9 else 6)`
- Это означает амортизированное O(1) добавление в конец

### **Асимптотика операций**

| Операция | Сложность | Комментарий |
|----------|-----------|-------------|
| `lst[i]` (чтение) | O(1) | Прямой доступ по индексу |
| `lst[i] = x` (запись) | O(1) | Прямой доступ по индексу |
| `len(lst)` | O(1) | Размер хранится в объекте |
| `lst.append(x)` | O(1)* | Амортизированное, иногда O(n) при realloc |
| `lst.pop()` | O(1) | Удаление с конца |
| `lst.pop(i)` | O(n) | Сдвиг всех элементов после i |
| `lst.insert(i, x)` | O(n) | Сдвиг всех элементов после i |
| `x in lst` | O(n) | Линейный поиск |
| `lst.sort()` | O(n log n) | Timsort |
| `lst.reverse()` | O(n) | Разворот inplace |
| Срез `lst[a:b]` | O(b-a) | Копирование элементов |

### **Практический пример**
```python
# Плохо: O(n²) - каждый insert сдвигает элементы
lst = []
for i in range(10000):
    lst.insert(0, i)  # O(n) каждый раз

# Хорошо: O(n) - append амортизированное O(1)
lst = []
for i in range(10000):
    lst.append(i)  # O(1) каждый раз
lst.reverse()  # O(n) один раз
```

## **Tuple (кортеж) - неизменяемый массив**

### **Внутреннее устройство**

Tuple - это **неизменяемая версия списка**. Хранится как непрерывный блок указателей, но без возможности изменения.

```
Tuple (1, 2, 3) в памяти:
┌─────────────────┐
│  Tuple Object   │
│  ├─ size: 3     │
│  └─ items ──────┼──► [ptr1] [ptr2] [ptr3]
└─────────────────┘      ↓      ↓      ↓
                        int(1) int(2) int(3)
```

**Ключевые особенности:**
- Непрерывный блок памяти (как у list)
- Неизменяемый (immutable) - после создания нельзя изменить
- Более компактный, чем list (нет over-allocation)
- Кэшируется интерпретатором для маленьких tuple (до 20 элементов)
- Может использоваться как ключ словаря (если содержит только immutable элементы)

### Асимптотика операций

| Операция | Сложность | Комментарий |
|----------|-----------|-------------|
| `tup[i]` | O(1) | Прямой доступ |
| `len(tup)` | O(1) | Размер хранится |
| `x in tup` | O(n) | Линейный поиск |
| `tup.count(x)` | O(n) | Подсчет вхождений |
| `tup.index(x)` | O(n) | Поиск индекса |
| Создание tuple | O(n) | Копирование указателей |

### **Практический пример**
```python
# Tuple быстрее и компактнее
# Создание tuple на ~30% быстрее
t = (1, 2, 3)  # Быстрее, чем [1, 2, 3]

# Tuple занимает меньше памяти
import sys
print(sys.getsizeof([1, 2, 3]))   # 88 bytes
print(sys.getsizeof((1, 2, 3)))   # 64 bytes

# Tuple можно использовать как ключ словаря
d = {(1, 2): "point", (3, 4): "another point"}
```

## **Set (множество) - хэш-таблица**

### **Внутреннее устройство**

Set реализован как **хэш-таблица** (hash table) с открытой адресацией.

```
Set {1, 2, 3} в памяти:
┌─────────────────────────────────────┐
│  Set Object                         │
│  ├─ table ──────────────────────────┼──► [hash][key] [hash][key] [hash][key] ...
│  ├─ used: 3                         │      ↓        ↓        ↓        ↓
│  └─ mask: 7 (размер таблицы - 1)    │    1|hash1  2|hash2  3|hash3  empty
└─────────────────────────────────────┘
```

**Ключевые особенности:**
- Элементы должны быть хэшируемыми (immutable)
- Хэш-таблица с открытой адресацией (linear probing)
- Таблица всегда заполнена максимум на 2/3 (load factor)
- При превышении load factor таблица расширяется (resize)
- Порядок элементов не гарантирован (зависит от хэшей)

### **Асимптотика операций**

| Операция | Сложность | Комментарий |
|----------|-----------|-------------|
| `x in s` | O(1)* | Хэш-поиск, в худшем случае O(n) при коллизиях |
| `s.add(x)` | O(1)* | Амортизированное, иногда O(n) при resize |
| `s.remove(x)` | O(1)* | Хэш-поиск + удаление |
| `s.discard(x)` | O(1)* | Как remove, но без ошибки если нет |
| `s.pop()` | O(1) | Удаление произвольного элемента |
| `len(s)` | O(1) | Счетчик хранится |
| `s1 & s2` (пересечение) | O(min(len(s1), len(s2))) | Итерация по меньшему |
| `s1 \| s2` (объединение) | O(len(s1) + len(s2)) | Копирование обоих |
| `s1 - s2` (разность) | O(len(s1)) | Итерация по s1 |

### **Практический пример**
```python
# Плохо: O(n²) - поиск в list
lst = [1, 2, 3, 4, 5]
for i in range(10000):
    if i in lst:  # O(n) каждый раз
        pass

# Хорошо: O(n) - поиск в set
s = {1, 2, 3, 4, 5}
for i in range(10000):
    if i in s:  # O(1) каждый раз
        pass
```

## **Dict (словарь) - хэш-таблица с ключами**

### **Внутреннее устройство**
Dict также реализован как **хэш-таблица**, но хранит пары ключ-значение.

**С Python 3.6+ (компактное представление):**
```
Dict {'a': 1, 'b': 2} в памяти:
┌──────────────────────────────────────────────┐
│  Dict Object                                 │
│  ├─ indices ─────────────────────────────────┼──► [2] [0] [1] [empty] [empty] ...
│  │                                           │      ↓    ↓    ↓
│  └─ entries ─────────────────────────────────┼──► [hash_a|'a'|1] [hash_b|'b'|2]
└──────────────────────────────────────────────┘
```

**Ключевые особенности:**
- С Python 3.7+ порядок вставки сохраняется (официально)
- Компактное представление экономит ~20-25% памяти
- Ключи должны быть хэшируемыми
- Значения могут быть любыми объектами
- Load factor ~2/3, при превышении - resize

### **Асимптотика операций**

| Операция | Сложность | Комментарий |
|----------|-----------|-------------|
| `d[key]` (чтение) | O(1)* | Хэш-поиск |
| `d[key] = value` (запись) | O(1)* | Амортизированное |
| `key in d` | O(1)* | Хэш-поиск |
| `del d[key]` | O(1)* | Хэш-поиск + удаление |
| `d.get(key, default)` | O(1)* | Хэш-поиск с дефолтом |
| `d.keys()` | O(1) | View объект |
| `d.values()` | O(1) | View объект |
| `d.items()` | O(1) | View объект |
| `len(d)` | O(1) | Счетчик хранится |
| Итерация по `d` | O(n) | Обход всех элементов |

### **Практический пример**
```python
# Подсчет частоты элементов
# Плохо: O(n²)
text = "hello world"
freq = {}
for char in text:
    count = 0
    for c in text:  # O(n) каждый раз
        if c == char:
            count += 1
    freq[char] = count

# Хорошо: O(n)
from collections import Counter
freq = Counter(text)  # O(n) один раз
```

**List:**
- Нужен упорядоченный набор с возможностью изменения
- Частый доступ по индексу

## **Хеш таблицы**

### **Суть идеи**

**Хеш-таблица (hash table / hash map)** — структура данных, реализующая абстрактный тип «ассоциативный массив» (словарь: `key → value`) со средним временем `O(1)` на вставку, поиск и удаление.

Идея: вместо того чтобы искать ключ сравнением с другими ключами (как в списке — `O(n)`, или в дереве — `O(log n)`), мы **вычисляем из ключа номер ячейки массива**:

```
index = hash(key) % capacity
```

Массив называется **таблицей / бакетами (buckets)**, а функция `hash` — **хеш-функцией**.

**Ключевой инвариант:** одинаковые ключи всегда дают одинаковый хеш → одинаковый индекс. Поэтому достаточно посмотреть в одно место (или в небольшой окрестности), а не обходить всю коллекцию.

Три обязательных компонента:
1. Хеш-функция.
2. Способ разрешения коллизий (два разных ключа попали в один индекс).
3. Политика роста (рехеширование при заполнении).

**Что даёт `O(1)`, а что нет:**

| Операция | Сложность (среднее) |
|---|---|
| `d[key]`, `key in d`, `d[key] = v`, `del d[key]` | `O(1)` |
| Поиск минимума/максимума, `k`-й по порядку | `O(n)` |
| Диапазонный запрос (`все ключи от a до b`) | `O(n)` |
| Обход в отсортированном порядке | `O(n log n)` |
| Обход всех элементов | `O(n)` (точнее `O(capacity + n)`) |

Хеш-таблица **не хранит порядок по ключам** — это её главный принципиальный минус.

---

### **Хеш-функция**

### Требования (обязательно спрашивают)

1. **Детерминированность:** `a == b ⇒ hash(a) == hash(b)`. Это контракт №1.
2. **Согласованность с равенством** (обратное НЕ требуется): разные объекты могут иметь одинаковый хеш — это коллизия, и это нормально.
3. **Быстрота вычисления:** `O(1)` для чисел, `O(L)` для строки длины `L`.
4. **Равномерность (uniformity):** значения должны равномерно размазываться по всему диапазону, чтобы не было «горячих» бакетов.
5. **Лавинный эффект:** изменение одного бита входа меняет ~половину бит выхода. Иначе похожие ключи (`"user1"`, `"user2"`) лягут рядом.
6. **Стабильность в рамках жизни объекта:** хеш не должен меняться, пока объект лежит в таблице.

### Что НЕ требуется
- Криптостойкость. `hash()` в Python/Java — **не** криптографическая функция. Для паролей — bcrypt/argon2, для целостности — SHA-256. Это разные задачи: тут нужна скорость и равномерность, там — необратимость и стойкость к коллизиям.
- Отсутствие коллизий (невозможно, см. §3).

### **Коллизии неизбежны**

**Принцип Дирихле:** ключей больше, чем ячеек → коллизии гарантированы. Для строк/объектов ключей бесконечно много, а `hash` — конечное число бит.

**Парадокс дней рождения:** коллизия становится вероятной уже при `~√m` ключах, а не при `m`. При 32-битном хеше коллизия ожидается уже на ~77 000 ключах. Практический вывод: **нельзя строить систему, предполагая уникальность 32/64-битного хеша** (частый вопрос на System Design: «можно ли использовать md5 как ключ дедупликации?» — можно, но нужно осознавать вероятность и/или делать полное сравнение).

Отсюда: **хеш-таблица всегда должна уметь корректно работать при коллизиях**, и `hash(a) == hash(b)` ≠ `a == b`. Поиск всегда заканчивается **сравнением ключей через `==`**.

## **СТЕК (Stack)**

**Стек** — структура данных, работающая по принципу **LIFO (Last In, First Out)**: последний положенный — первый извлечённый. Как стопка тарелок.

Две базовые операции + чтение вершины:

| Операция | Смысл | Сложность |
|---|---|---|
| `push(x)` | положить на вершину | `O(1)` amortized |
| `pop()` | снять с вершины | `O(1)` |
| `peek()` / `top()` | посмотреть вершину, не снимая | `O(1)` |
| `is_empty()`, `size()` | | `O(1)` |

**Инвариант:** стек не поддерживает произвольный доступ по индексу (хотя на практике можно). Его сила — в ограничении доступа: только к вершине.

<img src = "https://habrastorage.org/r/w1560/getpro/habr/upload_files/e76/7c8/b5b/e767c8b5bfda3c1d67d736f8bd37d1e7.png">

### **Применения стека**

1. **Call stack** — вызовы функций, рекурсия.
2. **DFS** — итеративный обход графа/дерева.
3. **Парсинг и синтаксис** — скобки, выражения, RPN (обратная польская запись).
4. **Backtracking** — генерация перестановок, sudoku solver.
5. **Монотонный стек** — Next Greater Element, Largest Rectangle in Histogram.
6. **Undo/Redo** — история операций.
7. **Поддержка минимума/максимума** — MinStack/MaxStack.
8. **Преобразование рекурсии в итерацию** — явный стек вместо рекурсивных вызовов (защита от stack overflow).


## **ОЧЕРЕДЬ (Queue)**


**Очередь** — структура **FIFO (First In, First Out)**: кто первый встал, тот первый вышел.

| Операция | Смысл | Сложность |
|---|---|---|
| `enqueue(x)` / `push(x)` | добавить в хвост | `O(1)` |
| `dequeue()` / `pop()` | взять из головы | `O(1)` |
| `peek()` / `front()` | посмотреть голову | `O(1)` |
| `is_empty()`, `size()` | | `O(1)` |



### **Применения**

1. **BFS** — обход графа/дерева по уровням.
2. **Планировщики** — задачи в порядке поступления, round-robin.
3. **Буферы** — чтение/запись потоков данных.
4. **Sliding window** — скользящее окно с monotonic deque.
5. **Rate limiter** — хранение временных меток запросов.
6. **Топологическая сортировка** (алгоритм Кана) — очередь вершин с нулевой степенью входа.

## **КУЧА (Heap)**

**Куча (heap)** — это **приоритетная очередь** на основе почти полного бинарного дерева, удовлетворяющего **свойству кучи**:

- **Min-heap:** каждый узел ≤ своих детей. Корень — минимум.
- **Max-heap:** каждый узел ≥ своих детей. Корень — максимум.

**Представление в массиве** (бинарная куча, 0-индексация):
```
parent(i)     = (i - 1) // 2
left(i)       = 2*i + 1
right(i)      = 2*i + 2
```

Никаких указателей — только массив. Это даёт отличную cache locality.

| Операция | Сложность |
|---|---|
| `peek()` (мин/макс) | `O(1)` |
| `push(x)` | `O(log n)` |
| `pop()` (извлечь min/max) | `O(log n)` |
| `heapify` (построить из массива) | `O(n)` |
| `remove` произвольного элемента | `O(log n)` при наличии индекса |
| `decrease_key` / `increase_key` | `O(log n)` |
| `merge` двух куч (бинарная) | `O(n)` (плохо) |


На рисунке представлена куча типа `max-heap`, основанная на следующем правиле: дочерние элементы меньше родительского. Существуют также кучи min-heap, где дочерние элементы всегда больше родительского.

### **Добавление элемента в существующую кучу**

Алгоритм:
- Добавляем элемент в самый низ кучи.

- Сравниваем добавленный элемент с родительским; если порядок верный — останавливаемся.

- Если нет — меняем элементы местами, и возвращаемся к предыдущему пункту.

<img src = "https://habrastorage.org/r/w1560/files/58a/795/3e9/58a7953e9c704b5d86c848f669de9d4e.jpg">


### **Извлечение максимального элемента кучи**

Алгоритм:

- Заменить корневой элемент самым нижним.

- Сравнить новый корневой элемент с дочерними. Если они в правильном порядке — остановиться.

- Если нет — заменить корневой элемент на одного из дочерних (меньший для min-heap, больший для max-heap), и повторить шаг 2.

<img src = "https://habrastorage.org/r/w1560/files/36d/43a/ce3/36d43ace39b246778f5817640ebb6945.jpg">

### **Применения**

1. **Priority queue** — планирование задач, Dijkstra, A*.
2. **Top-K** — K largest/smallest.
3. **Merge K sorted lists.**
4. **Медиана потока** — две кучи (max-heap левой половины + min-heap правой).
5. **Scheduling** — задачи с дедлайнами.
6. **Алгоритм Хаффмана** — сжатие.
7. **K-th порядковая статистика.**
8. **Stock span, трафик-аналитика.**


## **ОДНОСВЯЗНЫЙ СПИСОК (Singly Linked List)**

**Односвязный список** — цепочка узлов, каждый хранит значение и указатель на следующий.

<img src = "https://habrastorage.org/r/w1560/getpro/habr/upload_files/e14/94f/35d/e1494f35d86c9ddd0c89fdee212e61f2.png">

| Операция | Сложность |
|---|---|
| Доступ по индексу | `O(n)` |
| Поиск значения | `O(n)` |
| Вставка в начало | `O(1)` |
| Вставка в конец (без tail) | `O(n)` |
| Вставка в конец (с tail) | `O(1)` |
| Вставка после известного узла | `O(1)` |
| Удаление по известному узлу (с prev) | `O(1)` |
| Удаление по значению | `O(n)` |
| Память на элемент | `O(1)` + оверхед указателя |

**Главное отличие от массива:** нет произвольного доступа, но есть `O(1)` splice (перелинковка) при известном узле.

### **Реализация на Python**

```python
class ListNode:
    __slots__ = ("val", "next")
    def __init__(self, val=0, next=None):
        self.val, self.next = val, next

    def __repr__(self):
        return f"ListNode({self.val})"


class SinglyLinkedList:
    def __init__(self):
        # Dummy head упрощает граничные случаи (вставка/удаление первого)
        self._head = ListNode()
        self._size = 0

    def __len__(self): return self._size

    def _node_at(self, index: int) -> ListNode:
        """Возвращает ПРЕДШЕСТВЕННИК узла с индексом index (для splice)."""
        if not (0 <= index <= self._size):
            raise IndexError(index)
        cur = self._head
        for _ in range(index):
            cur = cur.next
        return cur

    def insert(self, index: int, val) -> None:
        prev = self._node_at(index)
        prev.next = ListNode(val, prev.next)
        self._size += 1

    def append(self, val) -> None:
        self.insert(self._size, val)

    def remove(self, index: int):
        prev = self._node_at(index)
        if not prev.next: raise IndexError(index)
        removed = prev.next
        prev.next = removed.next
        self._size -= 1
        return removed.val

    def __iter__(self):
        cur = self._head.next
        while cur:
            yield cur.val
            cur = cur.next
```
### **Сравнение с массивом**

| | Массив (`list`) | Односвязный список |
|---|---|---|
| Память | непрерывная, cache-friendly | разбросана, оверхед на `next` |
| Доступ по индексу | `O(1)` | `O(n)` |
| Вставка в начало | `O(n)` | `O(1)` |
| Вставка в середину | `O(n)` (сдвиг) | `O(n)` (поиск) + `O(1)` splice |
| Splice при известном узле | `O(n)` | `O(1)` |
| Предсказуемость latency | хуже (resize, сдвиги) | стабильнее |

**Список выигрывает**, когда: нужны частые splice'ы по известным позициям (например, LRU-список, где мы держим указатели на узлы), нет resize'ов, важен стабильный latency.

**Список проигрывает** почти всегда на практике из-за cache misses. В Python `list` быстрее списка даже для вставки в начало на малых размерах.


### **Применения**

1. **LRU Cache** — обычно двусвязный, но односвязный тоже возможен (с хеш-таблицей на узлы).
2. **Реализация стека/очереди** (см. выше).
3. **Полиномы и символьные вычисления** — разреженные представления.
4. **Hash chaining** — цепочки коллизий в хеш-таблицах.
5. **Списки задач / цепочки зависимостей.**
6. **Undo-история** (односвязная — только назад).

# ШПАРГАЛКА: ВОПРОСЫ И КОРОТКИЕ ОТВЕТЫ

## Стек

**— LIFO или FIFO?** LIFO.

**— Сложности push/pop?** `O(1)` amortized для `list`.

**— Почему `list`, а не `deque`?** `list` непрерывен в памяти → лучше cache locality; `append`/`pop` — `O(1)`.

**— Что такое monotonic stack?** Стек, в котором элементы монотонны (возрастает/убывает). Решает задачи «найди следующий больший/меньший».

**— Как реализовать MinStack?** Пары `(val, cur_min)` или второй стек минимумов.

**— Где стек используется в реальности?** Call stack, DFS, парсинг, backtracking, RPN.

**— Что такое stack overflow?** Переполнение системного стека вызовов (глубокая рекурсия).

## Очередь

**— FIFO или LIFO?** FIFO.

**— Почему нельзя `list.pop(0)`?** Это `O(n)` — сдвиг всего массива.

**— Что использовать?** `collections.deque`.

**— Очередь на двух стеках — как?** Два стека `_in`, `_out`. При `dequeue` если `_out` пуст — переворачиваем `_in` в `_out`. Амортизированно `O(1)`.

**— Что такое circular buffer?** Кольцевой буфер фиксированного размера на массиве. Producer/consumer.

**— Monotonic deque — зачем?** Sliding window maximum/minimum за `O(n)`.

**— BFS использует что?** Очередь.

## Куча

**— Что такое куча?** Бинарное дерево в массиве со свойством: родитель ≤ (min-heap) или ≥ (max-heap) детей.

**— Сложности?** `push`/`pop` — `O(log n)`, `peek` — `O(1)`, `heapify` — `O(n)`.

**— Почему `heapify` — `O(n)`, а не `O(n log n)`?** Большинство узлов — листья, их не трогаем. Сумма по уровням = `O(n)`.

**— `heapq` — min или max?** Min. Для max — отрицание.

**— Как сделать max-heap из `heapq`?** Класть `-x`, при извлечении брать `-x`.

**— Что такое tie-breaker в куче?** Второе поле кортежа, чтобы при равных приоритетах не сравнивать несравнимые объекты. Обычно `counter`.

**— Top-K — как?** Min-heap размера K. Для каждого элемента: если больше минимума — заменить.

**– Медиана потока?** Две кучи: max-heap левой половины, min-heap правой. Балансируем.

**— D-heap vs бинарная?** D-heap (обычно d=4) быстрее на `push`, медленнее на `pop`. Лучше cache.

**— Fibonacci heap — зачем?** Теоретически: `decrease_key` за `O(1)` amor. Практически — проигрывает бинарной из-за констант.

**— Где куча в реальности?** Priority queue, Dijkstra, scheduling, Top-K, Huffman, медиана потока.

## Односвязный список

**— Сложности?** Доступ `O(n)`, вставка/удаление по известному узлу `O(1)`, вставка в начало `O(1)`.

**– Зачем dummy head?** Убирает граничные случаи с головой.

**— Fast/slow pointers — зачем?** Поиск цикла, середина списка, N-й с конца.

**— Как найти начало цикла?** После встречи slow/fast — один указатель в head, другой в точку встречи; идут по одному шагу, встречаются в начале цикла.

**— Reverse in-place — как?** Три указателя: `prev`, `cur`, `nxt`. Разворачиваем `next` у каждого.

**— Merge sort для списка?** Split пополам через slow/fast, рекурсивная сортировка, merge. `O(n log n)` времени, `O(1)` памяти (без рекурсивного стека — итеративно).

**— Палиндром?** Найти середину, развернуть вторую половину, сравнить.

**— Список vs массив?** Список — `O(1)` splice по известному узлу, нет resize. Массив — `O(1)` доступ, cache-friendly.

**— Когда список быстрее массива?** Когда нужны частые splice'ы по известным позициям (LRU, hash chaining) и важен стабильный latency.

**— Почему в Python `list` почти всегда быстрее?** Cache locality. Связный список — прыжки по куче.

**— Где список в реальности?** LRU (двусвязный), hash chaining, полиномы, цепочки задач.
